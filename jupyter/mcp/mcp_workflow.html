📖 四角色是怎么分工的

用户只说人话；MCP Host 是那个 AI 应用（Claude Code），里面跑着 LLM； MCP Client 负责和服务器「说 MCP 协议」；MCP Server 是真正干活的工具。 关键点：MCP 协议（蓝/青绿/橙色的线）只出现在 Client ⇄ Server 之间， 用户 ⇄ Host ⇄ Client 那几段（紫色虚线）是应用自己内部的事，不属于 MCP。 （在 Claude Code 里，Host 和 Client 常常打包在一起，但概念上它们是两个角色。）

0系统
Host 启动天气服务器
Claude Code（Host）启动时，按配置把 weather MCP 服务器作为子进程跑起来。
1MCP 请求 →
initialize
MCP 握手：Client 报身份、协商协议版本、声明能力。这是双方说的第一句话。
2MCP 响应 ←
initialize · 结果
服务器对「initialize」的回应。
3MCP 通知
initialized
通知：Client 告诉 Server「初始化完成，可以干活了」。通知没有 id，Server 不回话。
4MCP 请求 →
tools/list
工具发现：Client 问「你有哪些工具？」，Server 返回工具名和参数规范（schema）。
5MCP 响应 ←
tools/list · 结果
服务器对「tools/list」的回应。
6系统
Host 把工具登记给 LLM
Host 拿到工具列表后，把「有 get_alerts、get_forecast 两个工具可用」这件事告诉 LLM。以后 LLM 就能在需要时选择调用它们。
7阶段
阶段二 · 用户提问（每次对话都会发生）
8应用层
💬 提问
用户在 Claude Code 里输入：旧金山现在天气怎么样？
9系统
🤖 LLM 分析意图
LLM 判断：这个问题需要实时天气数据，自己没有，但有个 get_forecast 工具能查。于是决定调用它，参数取 旧金山（San Francisco） 的坐标 (37.7749, -122.4194)。
10应用层
指示调用 get_forecast
Host 把 LLM 的意图转成指令，交给 MCP Client 去执行（这一步是应用内部，不属于 MCP）。
11MCP 请求 →
tools/call · get_forecast
真正的 MCP 调用：Client 请求执行 get_forecast，查 旧金山（San Francisco） 的预报。Server 内部会去调用 weather.gov 的 API。
12MCP 响应 ←
tools/call · get_forecast · 结果
服务器对「tools/call · get_forecast」的回应。
13应用层
工具结果回传
Client 把 Server 返回的预报数据原样交回给 Host（也是应用内部）。
14系统
🤖 LLM 生成回答
LLM 拿到预报数据后，把它整理成一句自然语言，准备回复用户。
15应用层
回答用户
Host 把 LLM 生成的回答显示给用户。至此一次完整的工具调用闭环结束。
